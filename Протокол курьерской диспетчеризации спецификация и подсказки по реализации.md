# Протокол курьерской диспетчеризации: спецификация и подсказки по реализации

Умнее строить всё вокруг состояния, а не вокруг последовательности:

1. приём один и общий: в цикле приходит любая датаграмма, разбирается заголовок, по типу сообщения вызывается свой обработчик;
2. обработчик находит заказ (по OrderId) и курьера (по ключу), проверяет, допустимо ли сообщение в текущем статусе заказа, и только тогда меняет статус;
3. отправка случается в двух местах: как реакция на пришедшее сообщение (Ack, Go) и по таймеру (повторы, Order, heartbeat);
4. четыре шага «заказ → готов → начинай → начал» при этом нигде не записаны как последовательность вызовов. Они проявляются как цепочка переходов статусов, которую запускают приходящие сообщения.

*Семестровка по Socket (UDP), сервер и клиент курьера. Формат сообщений, правила надёжности, фазы заказа, таймеры и план реализации.*

Логика протокола придумана самостоятельно в ходе обсуждения, байтовый формат это черновик, который можно менять. Одно упрощение: после «начинай» клиент курьера автоматически отправляет «начал» (кнопка «начал» дала бы ещё одно окно решения человека, для семестровки это лишнее). Кнопки у человека три: **готов, отменил, доставил**.

## 1. Формат сообщения

Одно сообщение это одна датаграмма. Числа пишутся в сетевом порядке (big-endian).

| Поле | Размер | Зачем |
| --- | --- | --- |
| Magic | 2 байта | постоянная метка, чужое и мусор отбрасываются молча |
| Version | 1 байт | версия протокола |
| Type | 1 байт | тип сообщения |
| CourierKey | 16 байт (GUID) | ключ курьера (в сообщениях сервера ключ получателя) |
| OrderId | 4 байта | заказ, о котором речь (0, если нет) |
| Payload | зависит от типа | только у некоторых типов |

Заголовок фиксирован, 24 байта, поэтому любое сообщение разбирается одним кодом. Строки в Payload: UTF-8 с префиксом длины 2 байта. Размер всего сообщения держать ниже нескольких сотен байт.

## 2. Типы сообщений

| Код | Тип | От кого | Payload |
| --- | --- | --- | --- |
| 1 | Hello (вышел на линию) | курьер | нет |
| 2 | Bye (ушёл с линии) | курьер | нет |
| 3 | Ack | оба | 1 байт: тип подтверждаемого сообщения |
| 4 | Ready (готов) | курьер | нет |
| 5 | Started (начал) | курьер | нет |
| 6 | Cancel (отменил) | курьер | нет |
| 7 | Delivered (доставил) | курьер | нет |
| 8 | Heartbeat | оба | нет (в OrderId текущий заказ или 0) |
| 10 | Order (заказ) | сервер | адрес и описание (две строки) |
| 11 | Go (начинай) | сервер | нет |
| 12 | Revoked (отозван) | сервер | нет |

## 3. Правила надёжности

- **Ack автоматический**, отправляется сразу при получении, без участия человека. Подтверждать нужно всё, кроме Heartbeat и Revoked.
- **Повторы:** отправитель шлёт сообщение раз в секунду, пока не придёт Ack (или логический ответ), максимум N попыток.
- **Дубли:** повторное сообщение не выполняется второй раз, а только подтверждается заново. Решает состояние: заказ уже в такой фазе, значит, действие пропускается, а Ack отправляется.
- **Сообщение не по состоянию** (например, старое, пришедшее с опозданием) игнорируется, но подтверждается.
- **Revoked:** любое сообщение курьера про заказ, который за ним не числится (Ready, Started, Cancel, Heartbeat с таким OrderId), получает в ответ Revoked. Ни Ack, ни своих повторов у Revoked нет: сервер повторяет его сам в ответ на каждый heartbeat.
- **Heartbeat курьера:** раз в секунду, пока он на линии, с его текущим заказом или 0. **Heartbeat сервера:** раз в секунду курьеру, у которого заказ в фазах «Подтверждён» и «В работе».
- **lastSeen** курьера обновляется по **любому** его сообщению.

## 4. Фазы заказа и таймеры

| Статус | Ждём | Когда можно отдать другому |
| --- | --- | --- |
| Новый | свободного курьера | не назначен |
| Предложен | Ack на Order (повторы раз в 1 с, до N раз) | сразу после N неудач |
| Ждёт решения | Ready (окно 25 с у сервера, от момента Ack) | сразу пота  окну или при пропаже heartbeat |
| Подтверждён | Started или heartbeat с этим заказом | после S секунд тишины |
| В работе | Delivered | после S секунд тишины |
| Завершён |  |  |

**Единое правило:** отдавать сразу можно, только если курьер точно не мог начать. Если мог, то после того, как его аренда гарантированно истекла.

**Клиент курьера:** окно решения 20 с (от первого полученного Order, повторы его не сбрасывают). После Go он считается «в работе»: если от сервера нет **никаких** сообщений дольше C секунд, он сам отказывается от заказа.

## 5. Константы

Всё хранить в одном месте, в конфиге.

- heartbeat: 1 с; повтор сообщений: 1 с; N попыток: например 5;
- D (максимальная задержка сообщения): 2 с; C (аренда курьера): 9 с; S (сервер): 15 с; проверка **S − C > D**;
- окно решения: 20 с у клиента, 25 с у сервера (проверка: 25 − 20 > 2D, потому что путь проходится в обе стороны);
- свободный курьер становится «не отвечает» после, например, 5 с тишины.

## 6. Подсказки по реализации (C#)

**Структура решения:** три проекта: общая библиотека Protocol (enum типов, класс сообщения, сериализация и разбор), Server, Courier.

**Сокет:** `new Socket(AddressFamily.InterNetwork, SocketType.Dgram, ProtocolType.Udp)`. Сервер делает `Bind` на свой порт, клиент не биндится и получает порт от ОС. Принимать через `ReceiveFromAsync` (возвращает данные и `RemoteEndPoint`), отправлять через `SendToAsync`.

**Сериализация:** `BinaryPrimitives.WriteInt32BigEndian`, `Guid.TryWriteBytes(span)` и `new Guid(span)`. Разбор писать осторожно: сначала проверка длины, Magic, Version, известный ли Type. Любая ошибка означает «выбросить датаграмму», а не исключение.

**Сервер без static и без блокировок:** один цикл приёма складывает сообщения в `Channel<T>`, `PeriodicTimer` раз в секунду кладёт туда же «тик», а **один** потребитель обрабатывает всё по очереди. Так состояние заказов и курьеров меняет один поток, и гонок нет.

**Данные сервера:**

- заказ: Id, данные, Status, AssignedCourierKey, Attempts, время последней отправки, время Ack, множество **RejectedBy** (кто отказался или пропустил окно, чтобы заказ не вернулся тому же курьеру);
- курьер: Key, EndPoint (обновляется с каждым сообщением), State (свободен, занят, не отвечает), LastSeen, CurrentOrderId.

**Время:** мерить `Stopwatch` или `Environment.TickCount64`, а не часами системы.

**Консоль:** заказы создаются командой на консоли сервера (например `new <адрес>`), а курьер вводит `ready`, `cancel`, `done`.

**Порядок работы** (после каждого шага запускать и проверять):

1. Protocol: сериализация и разбор, проверка туда-обратно.
2. Hello и Heartbeat в обе стороны, словарь курьеров, «не отвечает».
3. Счастливый путь: Order → Ack → Ready → Go → Started → Delivered.
4. Все таймеры и возвраты в «Новый».
5. **Имитация потерь:** обёртка над отправкой, которая с заданной вероятностью роняет пакет или задерживает его. Это лучший материал для защиты: можно показать, что при потерях система не ломается.
6. Сценарии для показа: убить клиента посреди доставки, «заморозить» клиента (пауза в отладчике), потерять Ack, потерять Started.

## 7. Что решить самому

- где курьер хранит свой ключ (например, файл рядом с программой), чтобы после перезапуска остаться тем же курьером;
- как выбирать курьера из свободных (первый в списке или тот, кто дольше простаивает);
- как завершать работу курьера (отправка Bye).

## 8. Тезисы для защиты

- выбор UDP и два аргумента: сообщения приходят целиком, а открытое TCP-соединение при обрыве интернета не заменяет heartbeat;
- цена UDP: Ack, повторы и защита от дублей по состоянию написаны вручную;
- гарантия «никогда не двое на одном заказе» через аренду и формулы со своими числами;
- осознанный риск: максимальная задержка D это допущение, на UDP гарантировать её нельзя.
